# 要件定義: ステージ 5-1（改）

## はじめに

ワールド5の最初のステージ `5-1` を、仮ステージから**チームが設計した本番パズル**へ差し替える。テーマは「**倍数（割り切れる数）** と **while の抜け方**、**火力配分**」を体感させるフローチャートパズル。ボスは `black_wing_dragon`（ゴールデンバードの進化形）。プレイヤーは手札 11 枚のうち 10 枚を 10 個のスロット（1 枚はダミー）に配置し、実行して敵 HP を 0 にできればクリア。

本ステージは `src/data/stages.json` の `5-1` エントリ（＋必要なら `stagesLoader.js` が解釈する `flow` 構造）で表現する。既存のステージ（1-x〜4-x）やローダー・バトル実行ロジックには影響を与えない。設計の数値・構造は手書き原案（`5-1.png`）と作者の解説を source of truth とする。

### 定数・手札・解答（設計の確定値）

- 自分HP = 100 / 敵HP = 270 / 敵 = `black_wing_dragon`
- 手札（11枚）：攻20・攻15・攻10・攻6・攻5 ／ 防25・防10・防10 ／ 回30・回25 ／ カウンター
- 解答配置：`[1]`防10・`[2]`防25・`[3]`回25・`[4]`回30・`[5]`攻6・`[6]`カウンター・`[7]`防10・`[8]`攻10・`[9]`攻20・`[10]`攻15、**ダミー=攻5**

## 要件

### 要件1: ステージ対戦パラメータの提供
**ユーザーストーリー：** プレイヤーとして、ステージ5-1を開始したとき設計どおりの敵・HP・手札で始めたい。なぜなら、パズルの前提条件が設計と1つでもズレると解が成立しないから。

#### 受け入れ基準
1. WHEN プレイヤーがステージ `5-1` を開始する THEN the system SHALL 敵を `black_wing_dragon`、敵HPを 270、自分HPを 100 で初期化する
2. WHEN ステージ `5-1` が読み込まれる THEN the system SHALL 手札を「攻20・攻15・攻10・攻6・攻5・防25・防10・防10・回30・回25・カウンター」の11枚で提供する
3. WHEN ステージ `5-1` が読み込まれる THEN the system SHALL 配置可能スロットを 10 個（`[1]`〜`[10]`）用意し、`[1]` は防御カード専用（`acceptOnly: guard`）とする

### 要件2: フローチャート構造の忠実な再現
**ユーザーストーリー：** ステージ作者として、手書き原案のフロー構造をそのまま再現したい。なぜなら、while/for/条件分岐/倍率/敵カードの配置こそがパズルの難易度と学びを決めるから。

#### 受け入れ基準
1. WHEN フローが構築される THEN the system SHALL 先頭を `START →[1]→ 敵カード(-15) → 敵カード(-75)` の順にする
2. WHEN フローが構築される THEN the system SHALL **第1の while**「`敵HP > 240` の間ループ」を設け、そのボディ内に条件分岐「`自分HP ≤ 30`」を置く
   - true 経路：`[2] → 敵(-30) → [4]`
   - false 経路：`敵guard(5) → 敵(-40) → [3] → 敵(-5) → 敵guard(5)`
   - 両経路の合流後：`敵(-15) → [5]` を通ってループ先頭へ戻る
3. WHEN フローが構築される THEN the system SHALL **第2の while**「`自分HP < 60` の間ループ」を設け、ボディを `回復(+10)` 1個にする（HPが60以上になったら脱出）
4. WHEN 第2の while を抜ける THEN the system SHALL 続けて `敵(-60) → 回復(+45)` を通す
5. WHEN フローが構築される THEN the system SHALL **for ループ（5回）** を設け、そのボディを次の構造にする
   - 条件分岐「`ループが1,3,5回目か？`（周回カウンタが奇数）」
     - true：`[6] → 敵(-20) → [7] →(m1)→ 敵(-15) →(m2)→ [9]`
     - false：条件分岐「`自分HP ≤ 20`」 true→`(m1)` に合流／ false→`[8] → 敵(-15) →(m2)` に合流
6. WHEN for ループを抜ける THEN the system SHALL `[10]` に倍率 `×4` を付与し（攻15×4）、その後 `敵（ゴール）` へ接続する

### 要件3: 解答の成立とパズル意図の保全
**ユーザーストーリー：** プレイヤーとして、設計された解答で確実にクリアでき、かつ設計者が意図した「引っかけ」ではクリアできないようにしたい。なぜなら、それが成立して初めて「倍数・while脱出・火力配分」の学びが機能するから。

#### 受け入れ基準
1. WHEN プレイヤーが解答どおり（`[1]`防10…`[10]`攻15、ダミー攻5）に配置して実行する THEN the system SHALL 敵HPを 0 にし、かつ自分HPを 1 以上に保ってクリア判定する
2. IF 第1の while 内で高火力カード（攻20/攻15/攻10）を使う THEN the system SHALL 後半の for で火力不足となり、クリアできない結果にする（＝高火力は for 用に温存する設計）
3. WHILE 第2の while を回っている the system SHALL 自分HPが 60 未満の間 `+10` を繰り返し、65 で抜けなければ直後の `敵(-60)` で自分HPが 0 以下になり負けとなる（抜け方が HP 末尾 5 に定まる）
4. WHEN 設計どおり 65 で第2の while を抜ける THEN the system SHALL `敵(-60)→回復(+45)` を経て自分HPを 50 にし、for ループ開始時点の HP を 50 にする

### 要件4: 敵アクションカード（guard / heal / reflect）の表現
**ユーザーストーリー：** プレイヤーとして、敵の防御・回復・反射カードが見てわかる形で盤面に出てほしい。なぜなら、ワールド5はこれら敵カードの存在が攻略の鍵になるから。

#### 受け入れ基準
1. WHEN 敵カードがフロー上に現れる THEN the system SHALL `public` に配置済みのカードデザインに対応する `lockedCard`（敵guard/敵heal/敵reflect 等）として表示する
2. IF 敵カードの id が未定義・未配置 THEN the system SHALL NOT クラッシュせず、ローダーの既存フォールバックに従う

### 要件5: 既存ステージ・ローダーへの非回帰
**ユーザーストーリー：** 開発者として、5-1 の差し替えが他ステージや共通ロジックを壊さないようにしたい。なぜなら、1-x〜4-x は配信済み・検証済みの資産だから。

#### 受け入れ基準
1. WHEN 5-1 を差し替える THEN the system SHALL `stages.json` の他ステージ（1-1〜4-4, 5-2〜5-4）の定義を変更しない
2. WHEN 5-1 を差し替える THEN the system SHALL `stagesLoader.js` の既存 API・補完ルールを後方互換のまま使う（新規ノード種別を足す場合も既存ステージの出力を変えない）
3. WHEN 変更後にビルド・Lint を実行する THEN the system SHALL エラーなく通過する
