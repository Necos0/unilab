# 要件定義: なかまの城（レーン大戦争ミニゲーム）

## はじめに

本編（フローチャート型パズル RPG）とエンディングゲーム（コイン集め足場ゲーム）に続く、**3つめのおまけミニゲーム**。既存の 16 体の敵キャラクター（それぞれ idle／dead アニメ・`maxHp` を持つ）を再利用し、プレイヤーが **16 体から 6 体のデッキを組み、CPU とレーン戦（ニャンコ大戦争／クラッシュ・ロワイヤル型の陣取り）で対戦してハイスコアを目指す**単発マッチのゲーム。

- **起動は隠しコマンド `wqinouelabegg` のみ**（本編のメニューやマップUIからは入れない“知っている人だけのおまけ”）。
- おまけであるため、**本編・エンディングの進捗や状態には一切干渉しない**。
- キャラの**特殊能力は実装と並行して確定**していくため、能力はデータ駆動で後から足せる設計を前提にする（本要件では MVP の能力種別を例示するに留める）。
- **ゲームバランス（数値）の調整は継続的に行う**前提で、調整対象のパラメータを一箇所に集約する。

対象ユーザー：本編・エンディングをクリア済みで、隠しコマンドを知っている遊び手（主にプロジェクト作成者と、その周辺のプレイヤー）。

## 用語

| 用語 | 意味 |
|---|---|
| ミニゲーム | 本要件が定義する「なかまの城（レーン大戦争）」全体 |
| ロスター | 選択可能な既存キャラ 16 体（`enemies.json` の敵。`dragon_final` は当面ロスター外＝隠しボス扱い） |
| デッキ | プレイヤーが組む 6 体の編成（重複なし） |
| 手札 | デッキのうち画面に見えている先頭 3 枚 |
| ローテ | カードを出すとそのカードがデッキ最後尾へ回り、次のカードが手札に繰り上がる仕組み |
| エネルギー | 出撃に必要な資源（クラロワのエリクサー相当）。時間で回復し、上限あり |
| エスカレーション | 試合の経過時間に応じてエネルギー回復が速くなる仕組み（ダブルエリクサー相当） |
| ユニット | レーン上に出撃した 1 体のキャラ |
| 城（拠点） | 自陣・敵陣それぞれの HP を持つゴール。0 で決着 |
| チームカラー | 自分＝青／CPU＝赤 の識別色（足元オーラ） |
| CPU | 対戦相手のコンピュータ。プレイヤーと同じデッキ制で自動プレイする |

## 要件

### 要件1: 隠しコマンドでの起動と復帰
**ユーザーストーリー：** プレイヤーとして、隠しコマンド `wqinouelabegg` を打ったときだけこのミニゲームを起動し、終わったら元の画面に戻りたい。なぜなら、本編のおまけとして“知っている人だけ”がひっそり遊べるようにしたいから。

#### 受け入れ基準
1. WHEN プレイヤーが任意の画面で文字列 `wqinouelabegg` を打鍵する THEN the system SHALL ミニゲーム画面を開く
2. WHEN ミニゲーム画面を開く THEN the system SHALL 起動直前の画面を退避し、ミニゲーム終了時にその画面へ復帰できるようにする
3. IF プレイヤーが入力欄（名前入力など）にフォーカスしている、または修飾キー（Ctrl / Cmd / Alt）を同時押ししている THEN the system SHALL NOT コマンドを発動する（既存の隠しコマンドと同じガード方針）
4. WHERE 本編・エンディングのメニューやマップ上のボタン the system SHALL NOT このミニゲームへの導線を表示する（コマンド専用）

### 要件2: 本編・エンディングへの非干渉
**ユーザーストーリー：** プレイヤーとして、おまけを遊んでも本編の進捗がおかしくならないでほしい。なぜなら、ミニゲームはあくまで寄り道で、本編のセーブや解放状況を壊してほしくないから。

#### 受け入れ基準
1. WHILE ミニゲームがプレイ中 the system SHALL 本編の進捗（`progressStore`）・ガイド既読（`cutsceneStore`）・マップ位置（`mapStore`）・プレイヤー名（`playerStore`）を変更しない
2. WHEN ミニゲームを終了して元の画面へ戻る THEN the system SHALL 起動前と同じ本編状態を保つ
3. IF ミニゲーム用に永続化するデータ（ハイスコア等）がある THEN the system SHALL 本編セーブとは別のキーで保存する

### 要件3: デッキ編成（16体から6体）
**ユーザーストーリー：** プレイヤーとして、好きなキャラ 6 体を選んで自分のデッキを組みたい。なぜなら、「誰を入れて誰を外すか」を考えるのが面白さの中心だから。

#### 受け入れ基準
1. WHEN ミニゲームを開く THEN the system SHALL ロスター 16 体を一覧表示し、各キャラのコスト・HP など要点を示す
2. WHEN プレイヤーがロスターのキャラを選ぶ THEN the system SHALL そのキャラをデッキに加え、選択済みであることを明示する
3. WHEN 既に選択済みのキャラを再度選ぶ THEN the system SHALL そのキャラをデッキから外す
4. IF デッキが 6 体に達している WHEN プレイヤーがさらに別のキャラを選ぶ THEN the system SHALL 追加を受け付けない
5. IF デッキがちょうど 6 体（重複なし）である THEN the system SHALL 対戦開始を可能にする
6. IF デッキが 6 体未満である THEN the system SHALL 対戦開始を無効化し、残り必要枚数を提示する

### 要件4: 手札3枚とローテーション
**ユーザーストーリー：** プレイヤーとして、6 枚のうち 3 枚が手札として見え、出したカードは後ろに回るようにしたい。なぜなら、同じ強カードを連打できず「順番に来る 3 枚で今どう戦うか」という読みが生まれるから。

#### 受け入れ基準
1. WHEN 対戦が始まる THEN the system SHALL デッキ 6 枚の並びから先頭 3 枚を手札として表示する
2. WHERE 手札の隣 the system SHALL 次に手札へ入るカード（デッキ 4 番目）をプレビュー表示する
3. WHEN プレイヤーが手札のカードで出撃する THEN the system SHALL そのカードをデッキ最後尾へ移動し、繰り上がった新しい 3 枚を手札として表示する
4. IF あるカードを出した直後である THEN the system SHALL そのカードが手札に戻る前に、他のカードを 3 回出撃させる必要がある状態にする（デッキ 6・手札 3 の帰結）

### 要件5: エネルギーと出撃
**ユーザーストーリー：** プレイヤーとして、たまったエネルギーを使ってカードを出撃させたい。なぜなら、資源をいつ・何に使うかの判断が戦術になるから。

#### 受け入れ基準
1. WHILE 対戦中 the system SHALL エネルギーを時間経過で回復し、上限を超えないようにする
2. WHEN プレイヤーが手札のカードをタップ／クリックする AND エネルギーがそのカードのコスト以上ある THEN the system SHALL コスト分のエネルギーを消費してユニットを自陣から出撃させる
3. IF エネルギーがカードのコスト未満である THEN the system SHALL そのカードを出撃不可（無効表示）にする
4. WHEN 試合の経過時間が進む THEN the system SHALL エスカレーション（エネルギー回復の加速）を適用する（自分・CPU 双方に等しく）

### 要件6: レーン進軍と戦闘（idle／dead の再利用）
**ユーザーストーリー：** プレイヤーとして、出したユニットが自動で敵陣へ進み、ぶつかったら戦い、負けたら倒れてほしい。なぜなら、既存の idle／dead アニメだけで「行進→戦闘→撃破」が成立し、追加の絵がほぼ要らないから。

#### 受け入れ基準
1. WHEN ユニットが出撃する THEN the system SHALL そのユニットを自陣から敵陣方向へ自動で前進させる
2. WHILE ユニットが生存し進軍中 the system SHALL idle アニメを再生する
3. WHEN 進行方向の攻撃間合い内に敵ユニットがいる THEN the system SHALL 前進を止め、一定間隔で相手にダメージを与える（相手も同様に反撃する）
4. WHEN 進行方向に敵ユニットがおらず敵城が攻撃間合い内にある THEN the system SHALL 敵城にダメージを与える
5. WHEN ユニットの HP が 0 以下になる THEN the system SHALL そのユニットを撃破状態にして dead アニメを 1 回再生し、再生後にレーンから取り除く
6. IF プレイヤーは出撃時に配置位置を指定しない（MVP） THEN the system SHALL ユニットを常に自陣（レーン端）から出す

### 要件7: 特殊能力（データ駆動・拡張可能）
**ユーザーストーリー：** 開発者として、キャラごとの特殊能力を後から少しずつ足せるようにしたい。なぜなら、能力は実装と並行して決めていくので、エンジンを毎回書き換えずに追加・調整したいから。

#### 受け入れ基準
1. WHERE キャラに特殊能力パラメータ（例：攻撃間合い＝range、範囲半径＝splash、死亡時爆発＝deathbomb、および HP／攻撃／速さ／コストの上書き）が定義されている the system SHALL その値に従ってユニットの挙動を変える
2. WHEN 範囲攻撃（splash）を持つユニットが攻撃する THEN the system SHALL 着弾点の周囲一定範囲にいる敵すべてにダメージを与える
3. WHEN 遠距離（range が大きい）ユニットが攻撃する THEN the system SHALL 接触せず間合いの外から相手／敵城にダメージを与える
4. WHEN 死亡時爆発（deathbomb）を持つユニットが撃破される THEN the system SHALL そのユニットの周囲一定範囲の敵にダメージを与える
5. IF あるキャラに特殊能力が未定義である THEN the system SHALL そのキャラを通常の近接単体攻撃として扱う
6. WHEN 既存の能力種別（範囲・遠距離・死亡爆発・ステータス上書き）でまかなえる新キャラを追加する THEN the system SHALL エンジン本体の改修なしにデータ追加のみで対応できる

### 要件8: 敵と自分の見分け（向き＋チームカラー）
**ユーザーストーリー：** プレイヤーとして、同じ 16 体を両陣営が使っても、どちらが自分の味方か一目で分かるようにしたい。なぜなら、同キャラ同士や静止中でも敵味方が混同すると戦況が読めないから。

#### 受け入れ基準
1. WHEN ユニットを表示する THEN the system SHALL 自分のユニットに青、CPU のユニットに赤のチームカラー（足元オーラ）を付与する
2. WHEN ユニットを表示する THEN the system SHALL 自分のユニットを進行方向（右）向き、CPU のユニットを逆（左）向きに描画する
3. IF 自分と CPU が同じキャラを同時に出している、またはユニットが静止して戦闘している THEN the system SHALL チームカラーによって敵味方を判別可能にする
4. WHERE この識別方式（向き＋色）はロスターの全 16 体に適用できる the system SHALL 特定キャラ専用の追加立ち絵を必要としない

### 要件9: CPU 対戦（同じデッキ制で自動プレイ）
**ユーザーストーリー：** プレイヤーとして、CPU も自分と同じルール（6 枚デッキ・手札 3 枚・エネルギー）で戦ってほしい。なぜなら、同じ土俵で読み合うからこそ対戦として成立し、理不尽さが減るから。

#### 受け入れ基準
1. WHEN 対戦が始まる THEN the system SHALL CPU 用の 6 枚デッキを用意し、プレイヤーと同じ手札 3 枚・ローテ・エネルギー・エスカレーションの仕組みで動かす
2. WHILE 対戦中 the system SHALL CPU に、出せるカードがたまったら手札から選んで自陣（敵側）から出撃させ、出したカードを最後尾へローテさせる
3. WHEN CPU がカードを出す THEN the system SHALL 一定の間合い（間隔）を空けて出す（一度に全部を吐き出さない）
4. WHERE 難易度調整が必要 the system SHALL CPU のデッキ内容・出撃ペース・開始エネルギーで強さを変えられるようにする

### 要件10: 勝敗（城 HP）
**ユーザーストーリー：** プレイヤーとして、相手の城を先に落とせば勝ち、自分の城を落とされたら負け、というシンプルな決着にしたい。なぜなら、ゴールが明確なほど熱中できるから。

#### 受け入れ基準
1. WHEN 対戦が始まる THEN the system SHALL 自陣・敵陣それぞれに城 HP を設定して表示する
2. WHEN 敵城の HP が 0 以下になる THEN the system SHALL プレイヤーの勝利として対戦を終了する
3. WHEN 自陣の城の HP が 0 以下になる THEN the system SHALL プレイヤーの敗北として対戦を終了する
4. WHILE 対戦中 the system SHALL 両陣営の城 HP を常時ゲージ表示する

### 要件11: スコア計算（単発マッチ）
**ユーザーストーリー：** プレイヤーとして、1 戦の結果がスコアになり、上を目指せるようにしたい。なぜなら、同じ相手に「もっと上手く」勝つやり込みが生まれるから。

#### 受け入れ基準
1. WHILE 対戦中 the system SHALL スコアを、敵ユニットの撃破と敵城へ与えたダメージに基づいて加算し、現在値を表示する
2. WHEN プレイヤーが勝利する THEN the system SHALL 残り城 HP やクリア速度などのボーナスを加味して最終スコアを確定する
3. IF プレイヤーが敗北する THEN the system SHALL その時点までの到達度（撃破・与ダメージ）をスコアとして確定する
4. WHERE スコアの各係数（撃破点・与ダメージ点・ボーナス）は調整対象 the system SHALL それらを一箇所で変更できるようにする

### 要件12: ハイスコア（自己ベスト）の保存
**ユーザーストーリー：** プレイヤーとして、自己ベストが記録され、次に遊んだときも表示されてほしい。なぜなら、過去の自分を超える目標があると繰り返し遊びたくなるから。

#### 受け入れ基準
1. WHEN 対戦が終了して最終スコアが確定する AND そのスコアが保存済み自己ベストを上回る THEN the system SHALL 自己ベストを更新して保存する
2. WHEN ミニゲームの結果画面を表示する THEN the system SHALL 今回のスコアと自己ベストの両方を表示する
3. IF 今回が自己ベスト更新である THEN the system SHALL 更新であることを明示する
4. WHEN 自己ベストを保存する THEN the system SHALL 本編セーブとは別のキーでブラウザに永続化する

### 要件13: 結果画面と再戦／終了
**ユーザーストーリー：** プレイヤーとして、試合が終わったらその場で結果を見て、すぐもう一度遊ぶか、やめて元の画面へ戻るかを選びたい。なぜなら、テンポよく繰り返したいし、切り上げどきも自分で決めたいから。

#### 受け入れ基準
1. WHEN 対戦が終了する THEN the system SHALL 勝敗・今回スコア・自己ベストを含む結果画面をミニゲーム内に表示する
2. WHEN プレイヤーが結果画面で「もう一度」を選ぶ THEN the system SHALL 同じデッキで新しい対戦を開始する（城 HP・エネルギー・スコアを初期化する）
3. WHEN プレイヤーが結果画面で「終了（もどる）」を選ぶ THEN the system SHALL ミニゲームを閉じ、起動前の画面へ戻る（要件1-2）
4. WHERE 編成をやり直したい the system SHALL 結果画面または開始前から編成に戻れる導線を提供する

### 要件14: バランス調整パラメータの集約
**ユーザーストーリー：** 開発者（および調整を手伝う Claude）として、ゲームの手触りを数値だけで素早く調整したい。なぜなら、テンポやユニット強弱の調整を、ロジックを触らずに何度も試したいから。

#### 受け入れ基準
1. WHERE 調整対象の数値（各ユニットの HP／攻撃／速さ／コスト／特殊能力パラメータ、エネルギー回復量・上限、エスカレーション速度、城 HP、スコア係数、CPU の出撃ペース） the system SHALL それらをデータ／設定として一箇所に集約する
2. WHEN これらのパラメータを変更する THEN the system SHALL ゲームロジック（進軍・戦闘・勝敗・ローテ）のコードを変更せずに挙動へ反映する
3. IF 既存キャラの `maxHp` を基に初期値を自動算出する THEN the system SHALL その自動値を、上書きパラメータがある場合はそちらで置き換える

### 要件15: コードの隔離と最小接点
**ユーザーストーリー：** 開発者として、このミニゲームのコードを専用ディレクトリに隔離し、本編・エンディングのコードにできる限り触れずに済むようにしたい。なぜなら、本編は相方が担当しており、Claude に本編をいじらせるときに互いに干渉したり、ミニゲーム改修で本編を壊したりするのを避けたいから。

#### 受け入れ基準
1. WHERE ミニゲーム固有の実装（画面・ゲームロジック・データ／設定・ミニゲーム用フック） the system SHALL それらを専用ディレクトリ（例：`frontend/src/features/lanebattle/`）配下にまとめる
2. WHEN ミニゲームをアプリに組み込む THEN the system SHALL 共有コードへの変更を**単一のマウント地点**（例：`main.jsx` に `<LaneBattleGate />` を 1 箇所追加）に限定する
3. IF ミニゲームを組み込む THEN the system SHALL 既存の `App.jsx` の画面遷移・`useDebugCommands.js`・各ストアを変更しない（隠しコマンド `wqinouelabegg` の検出は、ミニゲーム側の自前リスナーで既存コマンドと同じガード方針を再現する）
4. WHILE ミニゲームが動作 the system SHALL 共有アセット（`frontend/public/sprites/enemies` のスプライト等）を**読み取り専用**で参照し、書き換えない
5. WHEN ミニゲームを丸ごと削除・無効化する THEN the system SHALL 専用ディレクトリの削除とマウント 1 行の除去だけで完結できる（本編にコードの痕跡を残さない）

## スコープ外（今回の要件では扱わない）

- キャラごとの**具体的な特殊能力の割り当て・数値**（実装と並行して確定。要件7の枠組みのみ定義）
- 複数ステージ／難易度選択、連戦・ウェーブ、拠点防衛モード（今回は**単発マッチ**のみ。将来拡張の候補）
- レーンの複数化やユニットの配置位置指定（MVP は 1 レーン・自陣端から出撃）
- オンライン対戦・ランキング共有（自己ベストは端末ローカルのみ）
- サウンド・派手な演出の作り込み（最小限の視認性エフェクト＝範囲リング・弾は要件7の範囲で扱う）

## 参考（この要件の前提となった検討）

- 起動コマンド文字列：`wqinouelabegg`（打鍵検出の考え方は既存の隠しコマンド群 `wq...`（`frontend/src/hooks/useDebugCommands.js`）に倣うが、**本要件では共有コードへの干渉を避けるため、検出はミニゲーム側の自前リスナーで実装する**＝要件15）
- ロスター実データ：`frontend/src/data/enemies.json`（16 体＋`dragon_final`。idle／dead アニメ・`maxHp`・`sizeRatio` を保持）
- 敵/自分の差別化は 3 案（別キャラ／向きのみ／向き＋色）を試作で比較し、**「向き＋チームカラー」を採用**（要件8）
- デッキ 6・手札 3、CPU も同ルール、エスカレーションで決着を付ける手触りは、企画プレゼンの実プレイ版で確認済み
