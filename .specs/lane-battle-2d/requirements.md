# 要件定義: 陣取り合戦 3レーン版（2.5D）

## はじめに

おまけミニゲーム「陣取り合戦」を、現在の 1 レーン（1 次元）から **3 レーン＋自陣内フリー配置** の 2.5D に作り替える。狙いは戦略性の向上で、特に「端からしか出せないと遠距離キャラが一強になる」問題を、**配置の自由度（前線ドロップ）** という構造で解消する。理工展の正式版としてこの 3 レーン版を提供し、既存の 1 レーン版は置き換える。ユニット 16 体・デッキ編成・エナジー・スコアといった既存資産は踏襲し、変更は「盤面（レーン＋前後配置）」と「CPU」に集中させる。想定プレイヤーは小学 5〜6 年生を中心としつつ、理工展の来場者は小学生に限らず中高生・大学生なども多いため、幅広い年齢・習熟度が楽しめることを目指す（ゲーム内テキストは引き続き小学生も読める「ふりがな＋やさしい語」を守る）。

対象外（このバージョンでは作らない）：
- リアルタイム対人戦（PvP）… 将来の拡張。ただし後から足しやすいよう設計面で配慮する（要件 8）。
- スコアのオンラインランキング（バックエンド）… 本体チームの別トラックで要件化する。
- 自陣内の「連続」自由配置 … 当面は前後 3 段階の離散。連続化は将来の目標（要件 2 の将来拡張）。

## 要件

### 要件1: 3 レーンの戦場
**ユーザーストーリー：** プレイヤーとして、上・中・下の 3 つのレーンから出撃先を選びたい。なぜなら「どのレーンに投資し、どこを捨てるか」という読み合いを楽しみたいから。

#### 受け入れ基準
1. WHEN 対戦画面が開始する THEN the system SHALL 上・中・下の 3 レーンを持つ戦場を表示する
2. WHEN プレイヤーがカードを出す THEN the system SHALL 出撃するレーン（上／中／下）を選択させる
3. WHILE ユニットが生存している the system SHALL そのユニットを所属レーン内で敵陣方向へ前進させる（レーンをまたいだ移動はしない）
4. WHEN 同一レーンに敵味方のユニットがいて射程内に入る THEN the system SHALL 交戦（停止して攻撃）させる
5. WHERE ユニットが範囲攻撃（splash）を持つ場合 the system SHALL 同一レーン内の範囲に効果を及ぼす（レーンをまたぐ効果の有無は設計で決める）
6. WHEN ユニットが行動する THEN the system SHALL 射程（攻撃が届く距離）とは別に「探知距離」（敵を見つけられる距離。射程よりほんの少し長い）を持たせ、探知距離内で最も近い敵を標的にする
7. IF 標的が射程より遠い（探知距離内で前方にいる）場合 THEN the system SHALL レーン内を前進して標的を射程内に収める
8. IF 標的が探知距離内の後方（自陣側）にいる場合 THEN the system SHALL レーンを後退して標的を射程内に収める（自陣側に置かれた敵や、すれ違ってしまった敵にも向き直って対応できるようにする）

### 要件2: 自陣内フリー配置（前後 3 段階）
**ユーザーストーリー：** プレイヤーとして、自分の陣地の中なら前後どこに出すかを選びたい。なぜなら前線にドロップして、進んできた遠距離キャラを迎え撃ちたいから。

#### 受け入れ基準
1. WHEN プレイヤーがレーンを選んで出撃する THEN the system SHALL 自陣（フィールドの自分側の半分）の中で前後 3 段階（後方／中／前方）から配置位置を選ばせる
2. IF 配置先が敵陣側（中央ラインより敵側）の場合 THEN the system SHALL その配置を許可しない（自陣内にのみ配置できる）
3. WHEN 近接ユニットを「前方」に配置する THEN the system SHALL そのユニットを中央ライン付近から始動させ、前進してくる敵の遠距離ユニットと早期に交戦できるようにする
4. WHERE 前方寄りに配置した場合 the system SHALL 敵陣に近いほど相手のカウンターが届きやすい状態にする（リスクとリターンを釣り合わせる。具体的なブレーキ＝登場ディレイ等は設計で決める）
5. （将来拡張・このバージョンでは対象外）自陣内の配置を 3 段階の離散ではなく連続位置にできること

### 要件3: ユニット・デッキ・エナジー・スコアの踏襲
**ユーザーストーリー：** 開発者として、既存の 16 体・デッキ編成・エナジー・スコアの仕組みを流用したい。なぜなら理工展までに最短で仕上げ、変更を盤面と CPU に集中させたいから。

#### 受け入れ基準
1. WHEN デッキ編成を行う THEN the system SHALL 既存の 16 体ロスターから 6 枚を選ばせ、対戦中は 3 枚ずつ手札に見せる（出したカードは最後尾に回す）
2. WHEN 対戦が進行する THEN the system SHALL 既存のエナジー方式（上限・自然回復・時間経過での加速）でカード出撃を制御する
3. WHEN 対戦が始まる THEN the system SHALL 制限時間を設ける
4. WHEN 制限時間内に敵本陣を倒しきる THEN the system SHALL 一定の勝利点＋残り時間ボーナスでスコアを算出する
5. IF 勝ちきれなかった場合（制限時間に達した／自本陣が先に落ちた）THEN the system SHALL 敵本陣へ与えたダメージ量に応じてスコアを算出する（努力が点数に反映され、全員が最低点になりにくくする）
6. WHEN スコアが確定する THEN the system SHALL ベストスコアを保存する
7. IF レーン戦のバランス上必要になった場合 THEN the system SHALL 各ユニットの性能値・コスト・射程・スコア係数・制限時間・時間ボーナス係数などの数値を調整してよい（仕組みは踏襲し、数値は完成形を見て調整する）

> 補足：スコアの「算出式」だけは既存の減点方式から上記へ差し替える（3 レーン化でこう着による最低点は減る見込みだが、勝敗と努力がスコアに反映されるようにするため）。デッキ・エナジー・ベスト保存の仕組みは踏襲する。

### 要件4: 反応型 CPU
**ユーザーストーリー：** プレイヤーとして、歯ごたえのある CPU と戦いたい。なぜなら、ただランダムに出してくる相手では戦略で勝つ手応えが無いから。

#### 受け入れ基準
1. WHILE 対戦中 the system SHALL CPU に盤面（各レーンのプレイヤーユニットの脅威量）を評価させる
2. WHEN CPU が出撃を判断する THEN the system SHALL 脅威量の大きいレーンを優先し、手札の中から相性の良いカウンター（例：タンク→遠距離／範囲、群れ→範囲、遠距離→近接）を選ばせる
3. WHEN CPU がカウンターを出す THEN the system SHALL それを迎撃に有効な前後位置（前線など）へ配置させる
4. IF 差し迫った脅威が無い場合 THEN the system SHALL CPU にエナジーを温存させるか、優位なレーンへ計画的な攻めを行わせる
5. IF the system は CPU の意思決定に「適応・学習・探索」を用いない（ルールベースの反応で成立させる）

### 要件5: 難易度の調整（ダイヤル）
**ユーザーストーリー：** 開発者として、CPU の強さを数値で調整したい。なぜなら小 5〜6 が「サボると負ける／考えれば勝てる」と感じる塩梅にしたいから。

#### 受け入れ基準
1. WHERE 難易度パラメータが設定されている the system SHALL CPU の「反応の速さ（判断間隔）」「カウンター精度（最適手を選ぶ確率）」「エナジーの攻め度・回復倍率」を数値で変えられるようにする
2. WHEN CPU が最善手を外す設定になっている THEN the system SHALL 一定確率で非最適な行動（遅延・雑な選択）を取り、理不尽に強くならないようにする
3. IF 難易度が最大でない場合 THEN the system SHALL 思考のあるプレイヤーが勝てる余地を残す（無敵の CPU にしない）
4. WHERE 来場者の年齢・習熟度が幅広い（小学生〜大学生）ことを踏まえ the system SHALL プレイヤーが難易度（例：やさしい／ふつう／むずかしい）を選べるようにし、5-1 のダイヤルを難易度プリセットとして束ねる

### 要件6: 勝敗条件
**ユーザーストーリー：** プレイヤーとして、明確な勝ち負けの条件で戦いたい。なぜなら何を目指せばよいか分かるようにしたいから。

#### 受け入れ基準
1. WHEN 対戦が始まる THEN the system SHALL 各陣営に本陣（守り神）を用意し、その体力（HP）を表示する
2. WHEN ユニットが敵の本陣に到達する THEN the system SHALL 本陣の HP を削る
3. WHEN 敵本陣の HP が 0 になる THEN the system SHALL プレイヤーの勝ちとする
4. WHEN 自本陣の HP が 0 になる THEN the system SHALL プレイヤーの負けとする
5. WHEN 対戦を構成する THEN the system SHALL 本陣を各陣営 1 つに集約する（レーンごとの塔は設けない）。どのレーンのユニットも共通の本陣を攻撃・防衛する
6. WHEN 制限時間に達しても決着しない THEN the system SHALL タイムアップで対戦を終了する（勝敗はつかず、スコアは要件 3 の与ダメージ方式で決まる）

> 決定理由：レーンごとの塔はクラロワ的すぎるうえ、塔が残り 1 つになると結局「1 レーンへの押し込み対決」に戻ってしまうため、本陣は 1 つに集約する。

### 要件7: 1 レーン版の置き換えと隔離の維持
**ユーザーストーリー：** 開発者として、この 3 レーン版を正式版として 1 レーン版と入れ替えたい。なぜなら理工展では 3 レーン版だけを提供し、かつ本編開発への干渉を避けたいから。

#### 受け入れ基準
1. WHEN 3 レーン版を導入する THEN the system SHALL 既存の 1 レーン版の実装を置き換える（両立モードは作らない）
2. IF ミニゲーム関連の実装を変更する THEN the system SHALL それを `frontend/src/features/lanebattle/` 配下に収める
3. WHEN 本編コードへ触れる必要が生じた場合 THEN the system SHALL 変更を最小限（起動導線など既存の範囲）にとどめ、本編のストア・画面ロジックへ侵入しない
4. WHEN 起動導線を提供する THEN the system SHALL 既存の入口（隠しコマンド／タイトルの「じんとりがっせん で あそぶ」ボタン）をそのまま使えるようにする

### 要件8: 非機能 ― 将来の PvP／ランキングに備えた設計
**ユーザーストーリー：** 開発者として、後から対人戦やランキングを足しやすい作りにしたい。なぜなら、今は単独プレイで出しつつ、将来の拡張で作り直しになるのを避けたいから。

#### 受け入れ基準
1. WHEN 対戦ロジックを実装する THEN the system SHALL シミュレーション（勝敗が決まる計算）を、描画や入力元から分離した「入力（＝どのカードを・どのレーン・どの位置に出したか）で駆動される決定的な処理」として構成する
2. WHERE 入力元を差し替えられる the system SHALL 「ローカルのプレイヤー」「CPU」「（将来）ネットワークの相手」を同じ入力インターフェースで扱えるようにする
3. WHEN スコアを確定する THEN the system SHALL 後からランキング送信を足せるよう、スコア算出を一箇所に集約する
